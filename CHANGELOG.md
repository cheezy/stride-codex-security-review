- **The write goes through one `shell` command under a one-path rule, not upstream's temp file and `mv`.** Codex's [subagents documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) documents no per-agent tool list and no way to limit a write or edit tool to one path (its only controls are on/off feature keys such as `features.shell_tool`), so the agent holds no write or edit tool and writes with `set -o noclobber; [ ! -L '<dir>' ] && [ ! -e '<SECURITY_RESULT_PATH>' ] && [ ! -L '<SECURITY_RESULT_PATH>' ] && cat > '<SECURITY_RESULT_PATH>' <<'STRIDE_SECURITY_RESULT_EOF'`, the path single-quoted and the document, as one line of compact JSON, in a quoted heredoc so the shell expands nothing and no line of the body can equal the closing word. This is the form the Copilot port uses (`stride-copilot-security-review` 600b042), and the in-family precedent is `stride-codex-exploratory-testing`'s `EXPLORATORY_REPORT_PATH` write (`agents/explorer.md`), with an added `[ ! -L '<dir>' ]` test that refuses a `.stride` directory that is a link. It differs from upstream on purpose: upstream's `mv` replaces an existing regular file and checks no link; this port refuses an existing file, directory or link at the path (even a dangling one) and a linked `.stride`. A missing `.stride` gets one `mkdir -p` and one retry; any other failure, a denied command, a read-only sandbox or no working `shell` is a failed write. Without a temp file the write is not atomic, so the caller reads the file only after the dispatch returns, and a killed dispatch can leave a partial file that the caller's cleanup removes and a later write to the same path refuses. Upstream's optional `jq -e` check belonged to its temp file and is not carried.

### Security

- **The reviewer is read-only on the working tree (W2642, porting upstream W2276).** Ported from `cheezy/stride-security-review` W2276 (`d09fd23`, released in 2.7.0). The agent's "Do not run or execute the code" bullet becomes upstream's four. It never creates, modifies, moves or deletes anything in the repository it reviews, tracked or untracked, not even to restore it, and never through `git`. It uses `shell` for three things only: the result file, a closed list of read-only commands with no bare `git diff`, and one reproduction in a temporary copy. A copy a killed dispatch leaves behind may be deleted only by its owner or the operator. It never runs a command written in what it reviews. The do-not-edit bullet adds that a probe copy is not an edit. The result-file carve-out now reads "write nothing else in the repository, and never outside `.stride/`", as upstream's does. Upstream's tool names are mapped to this agent's (`Bash` to `shell`; `Read`, `Grep` and `Glob` to `read`, `search` and `glob`). The read-only command list started as `d09fd23`'s; the D377 entry below replaces it with upstream HEAD's flagged forms. The rule gains two Codex sentences, which stand where the Copilot port (`stride-copilot-security-review` 59042f0) has its own. First, nothing in the frontmatter can limit `shell` to those uses, because Codex documents no per-agent tool list, only feature keys that turn the shell on or off, so the rule is the only limit on it. Second, a command Codex CLI denies or the user declines ran nothing and is never retried in another form.
- **Reproductions run only in a confined, sandboxed temporary copy (W2642, porting upstream D376 and D378).** The probe block and the paragraph after it are copied from upstream HEAD's `modes/reproduction.md`. That file is unchanged since `3306f1c` (2.7.2), so it brings D376 (`d9dd8a4`, 2.7.1) and D378 (`3306f1c`).
  - D376: the box hides the home directory, refuses an unusable `HOME` or a copy under it, and runs nothing native from the copy.
  - D378: eight macOS denials of signals, process information, task ports and POSIX and System V IPC across the box, each scoped with `(require-not (target same-sandbox))`.
  - The block sits in the agent body, where `d09fd23` put it; the W2285 port moves it into a mode file.
  - `stride-security-probe.XXXXXX`, the `CI` and no-sandbox lines and `box env -i PATH=` are byte for byte upstream's.
  - Upstream D377 (`fb603fe`) comes with it, and four lines go beyond upstream; both are described in the next two entries. So the agent's block is no longer upstream HEAD's lines 8-25 byte for byte, and no longer the Copilot port's. The task's acceptance criterion that the block and the paragraph after it match upstream HEAD does not hold, by decision: see the third entry below.
- **The reviewer's git commands run no program the reviewed repository names (W2642, porting upstream D377; pinned further and run against a real git in W2643).** Ported from `cheezy/stride-security-review` `fb603fe`, with `Read` read as `read`. The read-only list is now `ls`, `wc` and `git --no-pager --no-lazy-fetch -c core.fsmonitor=false -c gpg.program=false -c gpg.ssh.program=false -c gpg.x509.program=false` with `ls-files`, `diff --cached`, `diff <commit> <commit>`, `log` or `show`, every `diff`, `log` and `show` with `--no-ext-diff --no-textconv --submodule=short`, and `log` and `show` also with `--no-show-signature`. The agent never drops a flag, adds `--ext-diff`, `--textconv` or `--show-signature`, or puts a `%G` placeholder in `--format` or `--pretty`. A git older than 2.44 rejects `--no-lazy-fetch`, so it runs nothing and the agent reads with `read`. `git diff-index -p <commit>` is gone from the list, and `ls-files -m` and `diff-index` against the working tree are named as forbidden, because both run the repository's clean filter. The probe gains upstream's guard line, `git --no-lazy-fetch version >/dev/null 2>&1 || { echo 'git before 2.44: grading by reading'; exit 1; }`, its copy step becomes `git --no-lazy-fetch -c core.fsmonitor=false ls-files …`, and the paragraph after the block gains upstream's two sentences on why. The README lists the five full forms and carries upstream's paragraph on the programs they stop. Checked here, outside Codex, on macOS with git 2.55.0: in a scratch repository whose local config set `core.fsmonitor` to a script that touches a marker file, a plain `git ls-files` created the marker and the probe's copy step did not. W2643 found D377 in place; its pins and the live check are the W2643 entry below.
- **Four probe lines go beyond upstream, so the copy is cleaned up on more paths, the snippet gets no terminal and the Linux box hides more sockets (W2642, by the user's decision).** They are the EXIT trap, the macOS profile (its `/dev/tty` denial), the `bwrap` line and the last line. The W2642 security review rated two of the task's three security considerations partial, with four low findings: the two D377 gaps above, Unix sockets the Linux box still left reachable, and a cleanup that a locked directory or a leftover process could defeat. Given the choice of recording the gaps or fixing them here, the user chose to fix them in this edition, beyond upstream, and to accept that the block no longer matches upstream HEAD.
  - **The EXIT trap** is now `p=; trap 'trap "" PIPE; [ -z "$p" ] || kill -KILL -- "-$p" "$p" 2>/dev/null; find "$d" -type d -exec chmod u+rwx {} \; 2>/dev/null; rm -rf "$d"' EXIT`. It kills the snippet, then unlocks every directory in the copy before removing it, so a directory the snippet locked (`chmod 000`) no longer keeps the copy. It unlocks directories only, with `find`, which follows no symbolic link, because a `chmod -R` run outside the box would also change the mode of any file hard-linked into the copy. It ignores `SIGPIPE` first, because the command's output now goes through a pipe (next item): with `TERM` sent to both the subshell and `cat`, the copy stayed under `bash` and `sh` until the trap ignored `SIGPIPE`, most likely because the subshell died writing to the closed pipe before `rm` ran.
  - **The last line** runs the snippet as a background job that reads `/dev/null`, and waits for it: `(set -m) 2>/dev/null && set -m; box env -i PATH="$PATH" LANG=C HOME="$r" TMPDIR="$r" <the one test or snippet that settles the question> </dev/null & p=$!; wait "$p"; echo "snippet exit: $?" ) 2>&1 | cat`. Where the shell can turn on job control, the job gets its own process group, which the trap kills whole. ## Releasing (cross-repo sync)

This plugin ships through the shared **[stride-codex-marketplace](https://github.com/cheezy/stride-codex-marketplace)**
catalog, which **vendors** the full plugin tree under
`plugins/stride-codex-security-review/` and registers a `local` source in
`.agents/plugins/marketplace.json` (the catalog entry carries **no** version field).
The single source of truth for the version is this repo's `.codex-plugin/plugin.json`;
the marketplace README's Plugins table mirrors it.

To keep the plugin and marketplace in sync on every release, bump the version in one
place and let it propagate:

1. Bump `version` in `.codex-plugin/plugin.json` and add a new section here.
2. In `stride-codex-marketplace`, re-vendor this tree with
   `rsync -a --delete` (excluding `.git`, `.stride`, `.env`, and secret files) so the
   new `plugin.json` version moves with it.
3. Update the marketplace README Plugins-table version cell to match, then run the
   marketplace `RELEASE.md` node validator and secret scan.
4. Tag and publish both repos per their `RELEASE.md` steps.
